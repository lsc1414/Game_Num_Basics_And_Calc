# Specs 规范指南

## Specs 的作用

在 Project Vampirefall 文档库中，specs 用于规范化地创建新的设计文档、技术文档或系统分析。每个 spec 代表一个完整的文档开发流程，从需求到设计再到实施。

## Spec 适用场景

### 适合创建 Spec 的情况
- 新增完整的游戏系统设计文档（如新的战斗机制、经济系统）
- 创建新的技术架构文档（如新的 AI 系统、渲染管线）
- 编写深度的游戏分析报告（如新的知识图谱、案例研究）
- 制定新的开发标准或工作流程
- 大型重构或改进现有文档体系

### 不适合创建 Spec 的情况
- 简单的文档修正或错别字修复
- 添加单个示例或代码片段
- 更新现有文档的小节内容
- 快速的参考资料补充

## Spec 文件结构

每个 spec 应放置在 `.kiro/specs/[feature-name]/` 目录下，包含：

```
.kiro/specs/[feature-name]/
├── requirements.md    # 需求文档（必需）
├── design.md         # 设计文档（必需）
└── tasks.md          # 任务清单（必需）
```

## Requirements.md 规范

### 文档结构

```markdown
# [功能名称] 需求文档

## 简介
[2-3 句话描述这个文档的目的和价值]

## 术语表
- **术语1**: 定义
- **术语2**: 定义

## 需求

### 需求 1: [需求标题]

**用户故事**: 作为 [角色]，我想要 [功能]，以便 [收益]

#### 验收标准

1. WHEN [触发条件] THEN 文档 SHALL [预期结果]
2. WHILE [状态] THEN 文档 SHALL [预期结果]
3. WHERE [可选特性] THEN 文档 SHALL [预期结果]

[重复其他需求...]
```

### 需求编写原则

1. **使用 EARS 模式**：
   - Ubiquitous: THE [系统] SHALL [响应]
   - Event-driven: WHEN [触发], THE [系统] SHALL [响应]
   - State-driven: WHILE [条件], THE [系统] SHALL [响应]
   - Unwanted: IF [条件], THEN THE [系统] SHALL [响应]
   - Optional: WHERE [选项], THE [系统] SHALL [响应]

2. **针对文档库的特殊考虑**：
   - 文档的完整性（是否包含所有必要章节）
   - 文档的可读性（结构、格式、示例）
   - 文档的准确性（技术细节、数值、引用）
   - 文档的可维护性（交叉引用、版本控制）
   - 文档的实用性（是否能指导实际开发）

### 示例需求

```markdown
### 需求 1: 系统设计文档完整性

**用户故事**: 作为程序员，我想要阅读完整的系统设计文档，以便理解如何实现该系统

#### 验收标准

1. WHEN 文档创建完成 THEN 文档 SHALL 包含系统概述、架构图、组件说明、数据流程和代码示例
2. WHEN 读者查阅技术细节 THEN 文档 SHALL 提供至少 3 个实际代码示例
3. WHERE 系统涉及性能优化 THEN 文档 SHALL 包含性能基准和优化建议
4. WHEN 文档引用外部资源 THEN 文档 SHALL 提供可访问的链接和引用说明
```

## Design.md 规范

### 文档结构

```markdown
# [功能名称] 设计文档

## 概述
[文档的整体设计思路]

## 文档架构
[章节组织方式、信息层级]

## 内容模型
[核心概念、术语定义、关系图]

## 正确性属性

*属性是应该在所有有效情况下都成立的特征或行为。*

### 属性 1: [属性名称]
*对于任意* [范围]，[应该满足的条件]
**验证需求**: Requirements X.Y

[更多属性...]

## 错误处理
[如何处理不完整、错误或过时的信息]

## 测试策略
[如何验证文档质量]
- 同行评审检查点
- 技术准确性验证
- 可读性测试
- 示例代码验证
```

### 正确性属性示例

针对文档库，正确性属性关注文档质量：

```markdown
### 属性 1: 代码示例可编译性
*对于任意* C# 代码示例，代码应该能够在 Unity 环境中编译通过（或明确标注为伪代码）
**验证需求**: Requirements 2.1

### 属性 2: 交叉引用一致性
*对于任意* 文档间的引用链接，目标文档应该存在且包含被引用的内容
**验证需求**: Requirements 3.2

### 属性 3: 术语使用一致性
*对于任意* 在术语表中定义的术语，在文档中应该使用统一的表述
**验证需求**: Requirements 1.3
```

## Tasks.md 规范

### 任务结构

```markdown
# [功能名称] 实施计划

## 任务清单

- [ ] 1. 创建文档骨架
  - 创建主文档文件
  - 设置章节结构
  - 添加占位符内容
  - _验证需求: 1.1, 1.2_

- [ ] 2. 编写核心内容
- [ ] 2.1 撰写概述和背景
  - 研究相关资料
  - 编写系统概述
  - 添加设计动机说明
  - _验证需求: 2.1_

- [ ]* 2.2 同行评审
  - 邀请团队成员审阅
  - 收集反馈意见
  - _验证需求: 2.1_

- [ ] 2.3 编写技术细节
  - 添加架构图（使用 Mermaid）
  - 编写实现说明
  - 提供代码示例
  - _验证需求: 2.2, 2.3_

- [ ]* 2.4 验证代码示例
  - 在 Unity 中测试所有代码
  - 确保编译通过
  - _验证需求: 2.3_

- [ ] 3. 添加参考资料
- [ ] 3.1 收集业界案例
  - 研究相关游戏实现
  - 添加案例分析
  - _验证需求: 3.1_

- [ ] 3.2 建立交叉引用
  - 链接到相关文档
  - 更新 readme.md
  - _验证需求: 3.2_

- [ ] 4. 最终检查
  - 确保所有链接有效
  - 验证 Mermaid 图表渲染
  - 检查中英文混排格式
  - 确认 emoji 使用恰当
```

### 任务编写原则

1. **可选任务标记**：使用 `*` 标记可选任务（如 `- [ ]* 2.2 同行评审`）
2. **需求追溯**：每个任务用 `_验证需求: X.Y_` 标注对应的需求
3. **渐进式完成**：任务应该可以增量完成，每个任务完成后文档都处于可用状态
4. **检查点**：在关键节点添加检查任务，确保质量

## 文档库特定的测试策略

### 文档质量验证

由于这是文档库而非代码库，"测试"主要指文档质量验证：

1. **结构完整性测试**
   - 检查所有必需章节是否存在
   - 验证章节层级是否合理
   - 确认目录结构符合规范

2. **内容准确性测试**
   - 代码示例编译验证
   - 数值公式计算验证
   - 技术细节事实核查

3. **可读性测试**
   - 同行评审
   - 新人理解度测试
   - 示例清晰度评估

4. **维护性测试**
   - 交叉引用链接检查
   - 术语一致性检查
   - 版本更新影响分析

### 示例测试任务

```markdown
- [ ]* 5. 质量验证
- [ ]* 5.1 代码示例验证
  - 在 Unity 2021.3+ 中测试所有 C# 代码
  - 确保命名符合 Unity_Standards 规范
  - 验证性能建议的有效性

- [ ]* 5.2 链接完整性检查
  - 使用工具检查所有内部链接
  - 验证外部链接可访问
  - 确认图片资源存在

- [ ]* 5.3 术语一致性审查
  - 对照术语表检查全文
  - 统一技术术语翻译
  - 确认 emoji 使用规范
```

## 工作流程

### 1. 创建新 Spec

```bash
# 在 .kiro/specs/ 下创建新目录
mkdir .kiro/specs/[feature-name]

# 创建三个必需文件
touch .kiro/specs/[feature-name]/requirements.md
touch .kiro/specs/[feature-name]/design.md
touch .kiro/specs/[feature-name]/tasks.md
```

### 2. 迭代流程

1. **需求阶段**：编写 requirements.md，明确文档目标和验收标准
2. **设计阶段**：编写 design.md，规划文档结构和内容模型
3. **实施阶段**：按照 tasks.md 逐步完成文档编写
4. **验证阶段**：执行质量检查任务，确保文档符合标准

### 3. 完成标准

一个 spec 被认为完成，当：
- [ ] 所有非可选任务已完成
- [ ] 文档已添加到 readme.md 的相应章节
- [ ] 所有代码示例已验证
- [ ] 所有链接已检查
- [ ] 至少一位团队成员已审阅

## 特殊考虑

### 知识图谱类文档

对于游戏分析类文档（如 `[GameName]_Knowledge_Map.md`），需求应包括：
- 游戏机制的完整性分析
- 数值模型的准确性
- 可借鉴设计的提炼
- 与 Project Vampirefall 的关联性

### 技术架构类文档

对于技术实现文档，需求应包括：
- 架构图的清晰度
- 代码示例的完整性
- 性能考虑的深度
- 与 Unity 最佳实践的一致性

### 标准规范类文档

对于规范类文档（如命名规范、工作流程），需求应包括：
- 规则的明确性和可执行性
- 示例的丰富性
- 工具支持（如验证脚本）
- 团队共识的体现

## 命名规范

### Feature Name 格式
使用 kebab-case：
- `tower-ai-system` - 塔防 AI 系统文档
- `loot-algorithm-analysis` - 掉落算法分析
- `unity-ecs-guide` - Unity ECS 指南
- `hades-build-diversity-study` - Hades 构建多样性研究

### 文档文件名
遵循项目现有规范：
- 使用下划线分隔：`Tower_AI_System.md`
- 知识图谱：`Hades_Knowledge_Map.md`
- 深度分析：`ECS_Performance_DeepDive.md`

## 与现有文档的集成

### 更新 readme.md

每个完成的 spec 必须在 readme.md 中添加链接：

```markdown
### 🤖 AI 与算法
*   **[塔防 AI 系统](Tech/AI/Tower_AI_System.md):** 基于效用的塔防目标选择。
```

### 交叉引用

新文档应该：
- 链接到相关的现有文档
- 在相关文档中添加反向链接
- 更新术语表（如果引入新术语）

## 最佳实践

1. **从小开始**：第一个 spec 选择较小的文档任务，熟悉流程
2. **迭代改进**：不要追求一次性完美，通过迭代逐步提升质量
3. **寻求反馈**：在设计阶段就邀请团队成员审阅
4. **保持一致**：遵循现有文档的风格和结构
5. **注重实用**：文档的最终目的是指导实际开发，不是为了文档而文档

## 常见问题

### Q: 什么时候需要创建 spec？
A: 当你要创建的文档需要多个步骤、涉及多个章节、需要研究和验证时，应该创建 spec。简单的文档更新可以直接修改。

### Q: 可以跳过某个阶段吗？
A: 不建议。即使是简单的文档，也应该先明确需求（为什么写）、再设计结构（怎么写）、最后实施（写什么）。

### Q: 如何处理文档的版本更新？
A: 重大更新应该创建新的 spec（如 `tower-system-v2`），小修小补直接修改即可。

### Q: 代码示例必须能运行吗？
A: 是的，除非明确标注为伪代码或概念示例。这是文档质量的重要保证。
